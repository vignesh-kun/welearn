# Dependency Management in WeLearn Monorepo

## System / Approach

The repository uses **npm** as its package manager for the Node/TypeScript codebase. Dependencies are declared in a single `package.json` at the workspace root, and a `package-lock.json` lockfile pins every transitive dependency to an exact version and integrity hash. There is no vendoring of npm packages (no `node_modules` committed), no private npm registry configuration, and no Go module files — this is a pure JavaScript/TypeScript project.

### Versioning strategy

- All dependencies use **caret (`^`) ranges** in `package.json`, e.g. `"next": "^16.1.1"`, `"react": "^19.0.0"`, `"@prisma/client": "^6.11.1"`. This allows minor/patch upgrades within the major version while still being constrained by the lockfile.
- The lockfile (`package-lock.json`, `lockfileVersion: 3`) records the exact resolved versions from the public npm registry (`https://registry.npmjs.org/...`).
- Dev-only tooling (eslint, typescript, tailwindcss, bun-types) lives under `devDependencies`; runtime libraries live under `dependencies`.

### Key files

- `package.json` — declares all runtime and dev dependencies, plus scripts.
- `package-lock.json` — deterministic lockfile generated by npm v7+.
- `.vercelignore` — Vercel deployment ignores; not a dependency file but relevant to what gets shipped.

### Build-time automation via postinstall

`package.json` defines:

```json
"postinstall": "prisma generate"
```

This means every `npm install` automatically runs `prisma generate` to regenerate the Prisma client against `prisma/schema.prisma`. It also exposes database-related scripts:

- `db:push` → `prisma db push`
- `db:migrate-all` → `tsx scripts/migrate-sqlite-to-supabase.ts`
- `db:seed` / `db:seed-words` → seeders under `scripts/`

### Scripts surface dependency usage

| Script | Purpose |
|---|---|
| `dev` | `next dev` |
| `build` | `next build` |
| `start` | `next start` |
| `lint` | `next lint` |
| `db:*` | Prisma + Supabase migration/seed helpers |

### No private registries or vendoring

A grep across the repo finds no `.npmrc`, no `GOFLAGS`, no `go.mod`/`go.sum`, and no `vendor/` directory. All packages resolve from the public npm registry. The only non-npm artifact is the `supabase/.temp/cli-latest` directory (a downloaded Supabase CLI binary used for local migrations).

### Notable dependency groups

- **Framework**: Next.js 16, React 19, TypeScript 5.
- **UI layer**: shadcn/ui built on Radix UI primitives (`@radix-ui/react-*`), Tailwind CSS v4, `tailwindcss-animate`, `tw-animate-css`, `class-variance-authority`, `clsx`, `tailwind-merge`.
- **State & data**: Zustand, TanStack Query, TanStack Table, React Hook Form + Zod resolvers.
- **Data layer**: Prisma (`prisma` CLI + `@prisma/client`) backed by Supabase PostgreSQL.
- **Utilities**: Framer Motion, date-fns, uuid, lucide-react icons, sonner toasts, embla-carousel, recharts, sharp (image processing).
- **Auth**: next-auth.
- **i18n**: next-intl.
- **Editor**: @mdxeditor/editor.
- **Custom SDK**: `z-ai-web-dev-sdk` (published to npm, version `^0.0.18`).

## Conventions and Constraints

- **Single-package manifest**: All dependencies are declared in the root `package.json`; there are no per-directory `package.json` files in this monorepo layout.
- **Caret ranges only**: Every entry in `dependencies` and `devDependencies` uses a `^` prefix — no tilde (`~`) or exact pinning in the manifest.
- **Lockfile required**: `package-lock.json` is committed alongside `package.json`, so CI and collaborators get deterministic installs.
- **Prisma client auto-generation**: The `postinstall` hook enforces that `prisma generate` runs after every install, ensuring the generated client stays in sync with `prisma/schema.prisma`.
- **No vendored node_modules**: Packages are fetched from npm on install; nothing is checked into source control.
- **No private registry configured**: There is no `.npmrc` or equivalent; all packages come from the public npm registry.
